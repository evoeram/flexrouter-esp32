# FlexRouter + ESP32: план работ (v3, по приоритетам)

> Прошивка ESP32-S3 для FlexRouter (ПТ Ту-154М, FS2004/FSUIPC). Базовая часть готова
> и проверена на стенде (см. п. 1). Этот план — только оставшиеся работы,
> упорядочены по приоритетам владельца проекта.
> Спецификация протокола ARCC — в п. 7 (зафиксирована, не меняется).
> Предыдущие версии плана: `plan.md` (v2), git `d584fb9` (v1).

---

## 1. Исходное состояние (без изменений с v2)

**Работает на стенде:** ввод (кнопка, энкодер, потенциометр-ось) и лампа-светодиод,
данные ходят в FlexRouter по COM (ARCC, 18-байтные пакеты).

**Готово в коде:** ARCC-ядро (приём/отправка, дампы, дребезг, ресинк), WiFiManager
provisioning, веб-морда (config/debug/admin, OTA, WS-монитор, /api/sim), конфиг в NVS,
TCP-сервер на плате (`transport.tcp`, порт 4001), Python-harness
(`Esp32/tools/arcc_harness/arcc_harness.py`).

**Ключевые факты из исходников FlexRouter** (для этапа 1):
- `Hardware/Arcc/ArccDevice.cs` — устройство на SerialPort; конструктор
  `(motherboardId, comPort)`; пакетные преобразования делегирует
  `ArccHardwareDataProcessor` (`ProcessDataFromSerialPort(byte[])` /
  `ConvertEventToByteArrayForHardware(ev)`) — **класс транспортно-независимый, переиспользуем как есть**.
- `Hardware/Arcc/ArccDevicesManager.cs : DeviceManagerBase` — обнаружение устройств:
  FTDI (Description starts with "ARCC") + USB VID-regex (`VID_303A` Espressif,
  `VID_1A86&PID_55D3` CH343). Плюс логика дампов (DumpLoop, ожидание 1 с тишины).
- `Hardware/Helpers/IHardwareDevice.cs` — интерфейс: `Connect/Disconnect/
  GetIncomingEvents/PostOutgoingEvents/Dump`.
- Веб-сервер платы поднимается **только в STA** (`main.cpp: webUp`), в AP порт 80
  занят порталом WiFiManager — главный блокер для приоритетов 2 и 3.

---

## 2. Приоритеты (зафиксированы владельцем)

1. **ArccNetDevice в FlexRouter** — транспорт B (TCP), избавление от USB-кабеля.
2. **Конфигуратор пинов в ESP-WebUI**, работающий даже без домашней точки доступа (в AP).
3. **Дебаг I/O в ESP-WebUI** (live-состояние всех устройств на плате), тоже в AP.
4. **74HC165 / 74HC595** — масштабирование входов/выходов.
5. Мелочи: опциональные ARCC-команды, конфликт GPIO48, multi-axis.

Всё остальное (реле/лампы 27В, физический индикатор, сверка с профилем Ту-154М) —
**отложено**, см. п. 6.

## 3. Этап 1 — ArccNetDevice (TCP-драйвер в FlexRouter)

Плата уже готова (`TcpArccTransport`, порт 4001, включается `"transport":{"tcp":true}`).
Нужна только PC-сторона.

- [x] **1.1. `ArccNetDevice : IHardwareDevice`** (новый файл `Hardware/Arcc/ArccNetDevice.cs`)
  - Копия структуры `ArccDevice`, вместо `SerialPort` — `TcpClient`/`NetworkStream`.
  - Конструктор `(motherboardId, host, port)`.
  - `Connect()`: TcpClient + KeepAlive; **нет DTR/CTS** — сразу считать готовым
    (это и есть смысл CDC/сети, см. `ArccDevice.Connect()` и его CTS-таймаут).
  - RX: читаем из NetworkStream в буфер → тот же
    `_arccHardwareDataProcessor.ProcessDataFromSerialPort(buffer)` (переименование
    метода не обязательно).
  - TX: тот же `SendDataLoop` / `ConvertEventToByteArrayForHardware`, потоку плевать
    на транспорт; `Thread.Sleep(2)` между пакетами сохранить.
  - Обрыв соединения: НЕ ронять потоки, выставлять флаг «link down», попытки
    реконнекта с backoff (1с → 5с → 15с). Реконнект не должен требовать рестарта
    роутера и повторного дампа (дамп — по желанию, см. 1.4).
  - `Disconnect()`: корректно закрыть TcpClient, остановить поток отправки.
  - `Dump(...)`: идентично `ArccDevice.Dump` (та же очередь outgoing).
- [x] **1.2. Регистрация устройств в `ArccDevicesManager`**
  - Сделано минимальным путём: **статический список адресов** — файл `ArccNetDevices.txt`
    рядом с FlexRouter.exe (строка = `host:port`, `#` — комментарий).
  - mDNS-обнаружение (`_arcc._tcp`) не потребовалось; сервис `http._tcp` на плате объявлен.
  - Приборы с суффиксом id `Arcc:NET_<host>_<port>`, чтобы не пересекаться с USB-устройствами.
- [x] **1.3. UI/конфиг**: реализован «ручной» путь из плана — правка `ArccNetDevices.txt`
  + документация (root README п. 6.1, `Esp32/README.md`). Редактор железа FlexRouter не менялся.
- [x] **1.4. Дампы через TCP**: по ревью кода `DumpLoop` адресуется через
  `Devices[motherboardId]` — транспортно-независим, работает с NET-устройством без изменений;
  ожидание «1 с без новых кнопок» на TCP тоже корректно (пакеты доходят сразу).
  Сквозная проверка на железе — в backlog (п. 1.5).
- [x] **1.5. Тесты**
  - Harness: TCP-режим дописан в `arcc_harness.py` (`--host 192.168.4.1 watch/selftest`).
  - Юнит-тесты на сборку/разбор пакетов уже есть (`ArccHardwareUnitTest.cs`, транспорт не участвует).
  - Сквозной FlexRouter↔плата — на железе (требует стенда).

## 4. Этап 2 — конфигуратор пинов в веб-морде (работает в AP)

**Блокер, который надо снять первым:** веб-сервер стартует только в STA
(`main.cpp: webUp`), в AP порт 80 занят WiFiManager.

- [x] **2.1. Свой AP-режим вместо портала WiFiManager** (вариант A, реализован)
  - WiFiManager полностью убран (и из `platformio.ini`). Нет кредов или 3 неудачи STA →
    `wifi_manager.cpp: startAp()`: `softAP("FlexRouter-Config")` **неблокирующе**,
    captive-DNS (все имена → 192.168.4.1).
  - `main.cpp: webUp` — при любом режиме ≠ BOOT: в AP работает **наш** `WebServerMgr`
    на 192.168.4.1; неизвестные URL (пробы ОС: /generate_204, /hotspot-detect.html,
    /connecttest.txt, …) → captive-редирект на морду (`web_server.cpp: onNotFound`).
  - AP-морда сама умеет сканировать сети (`/api/wifi/scan`) и сохранять SSID/пароль
    в конфиг (`/api/config` → `WifiMgr::reconfigure()`).
- [x] **2.2. Редактор pin map (config.html)**
  - Визуальный редактор: модули (id, тип), добавление/удаление/дублирование,
    добавление controlId (+ энкодер = пара Na/Nb), авто-выбор свободного пина.
  - Выпадающие списки GPIO: только свободные и валидные; зарезервированные и занятые
    видны в списке, но disabled с причиной. Резерв зашит в прошивку и отдаётся через
    `/api/pins/available`: USB D-/D+ (19/20), flash/PSRAM (26–37), UART0 (43/44),
    GPIO0 (BOOT), strap (45/46) + занятые другими controlId.
  - Параметры на модуль: `activeLow`, `rgb` (LinearOutput), для осей —
    `cal min/max` с кнопками «⟳ min/max» (через `/api/adc/read?pin=N`);
    `driver`/`cs/sck/mosi` у индикатора; `encoderDetent` — глобальный (как в прошивке).
  - Валидация на плате (POST /api/config): конфликт GPIO, зарезервированный/невалидный
    пин, дубль controlId, энкодер без второй фазы, ось на не-ADC → 400 с человекочитаемой
    ошибкой, показывается в UI (toast).
  - После сохранения модулей — автоматический ребут (уже был в `/api/config`).
- [x] **2.3. Отображение текущего состояния**: колонка «состояние» в редакторе —
  live-индикатор по WS-топику `io` (лампы горят/кнопки нажаты/маска BinaryInput/

- [ ] **2.4. Тест без домашней сети**: требуется железо (плата в AP → телефон →

## 6. Этап 4 — 74HC165 (входы) и 74HC595 (выходы)

- [ ] **4.1. Схема**: 165 — каскад (до 4 шт = 32 входа): data/clk/latch(/CE);
  595 — каскад под лампы: data/clk/latch. Питание 3.3В (логика совместима).
- [x] **4.2. Прошивка: модуль `ShiftIn`** (в `arcc_hw.h/.cpp`)
  - Конфиг: `{"id":1,"type":"ShiftIn","pins":{"data":..,"clk":..,"latch":..},"chips":2,
    "activeLow":true,"map":{"1":0,"2":1,...}}` (controlId → абсолютный бит каскада, до 4 чипов).
  - В `ArccHw::loop()` (1 кГц): latch → сдвиг `chips*8` бит → общий дребезг-конвейер
    (`debouncedStep`) → Button-пакеты (moduleId = id модуля).
  - Дампы: `dumpAllKeys` обрабатывает и ShiftIn-модуль.
- [x] **4.3. Прошивка: модуль `ShiftOut`**
  - Конфиг: `{"id":0,"type":"ShiftOut","pins":{"data":..,"clk":..,"latch":..},"chips":1,
    "activeLow":false,"map":{"10":0,...}}`.
  - Теневой регистр: `setLamp` меняет бит → `shiftOutLatch()` в конце цикла опроса
    (раз на цикл, не мигает мусором); activeLow поддержан.
  - rgb/WS2812 на ShiftOut не распространяются (только дискретные лампы).
- [x] **4.4. Веб-конфигуратор**: типы ShiftIn/ShiftOut в редакторе пинов —
  шина data/clk/latch, chips, карта «controlId → бит каскада»; валидация на плате
  (биты вне каскада/дубли, конфликт GPIO шины → 400 с текстом).
- [ ] **4.5. Тесты**: требуется макетка (16 кнопок через 2×165, 8 светодиодов через 595).
  Дамп и дребезг сквозь регистр — проверить на железе; код скомпилирован и принят
  платой (конфиг загружается, io/lamps/dump отвечают).

## 9. Спецификация протокола ARCC (кратко, зафиксирована)

- **PC → плата** (5/10 байт): Lamp `[4][mid][1][ctl][0|1]`;
  Indicator `[5][mid][1][7 кодов]`; дампы `[2|8][mid][3|2][0][0]`.
- **Плата → PC** (строго 18 байт, гуськом): Button `[2][mid]…[15]=ctl,[16]=0|1`;
  BinaryInput маска 28 линий в `[14..17]` BE; Encoder `[15]=ctl,[16]=щелчки,[17]=напр.`;
  Axis 8×2 байта BE (0..1023), ось j в байтах `[2+2j..3+2j]` (ControlId = 8−j).
- Serial 1250000 8N1 (для USB CDC формально); в начале потока возможен «призрачный» 0x00.
- Дамп при старте роутера обязателен; роутер ждёт до 1 с тишины как признак конца дампа.
- Полная версия — `git show d584fb9:plan.md` (п. 3).

## 10. Сборка/заливка

```
pio run -t upload                                # прошивка (USB-Serial-JTAG)
pio run -t buildfs && pio run -t uploadfs        # LittleFS (веб-морда)
pio run -e ledtest -t upload                     # отдельно тест led
```

FlexRouter: .NET 4.5, сборка через VS/msbuild; тесты — `FlexRouterUnitTests`.
