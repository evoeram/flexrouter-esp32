# Структура NN_pnk_154m_v1_40.gau и извлечение переменных

> ПТ Ту-154М v2.04 (Project Tupolev) — ПНК (пилотажно-навигационный комплекс)
> для FS2004. Разбор выполнен скриптом `analysis/extract_gau_variables.py`.

---

## 1. Структура файла GAU

`NN_pnk_154m_v1_40.gau` — это обычная **PE32 DLL** (x86), как и все .gau
файлы FS2004. «Декомпиляция» здесь = разбор PE-структуры + использование
map-файла сборки. Ключевые факты:

| Параметр | Значение |
|---|---|
| Формат | PE32 DLL (Machine i386), 14 619 648 байт |
| Экспорт | только `ImportTable` и `Linkage` (стандарт FS9) |
| Секции | `.text` 0x1000 (код, ~520 КБ), `.rdata` 0x83000 (константы/строки), `.data` 0x9C000 (глобальные переменные + BSS в хвосте), `.rsrc` 0x100000 (**13,5 МБ** — растровые ресурсы приборов), `.reloc` 0xDEA000 |
| Отладка | CodeView RSDS-запись → `d:\Prg\FS9_Prg\Tu-154M\PNK_154M\!Release\PNK_154M.pdb` (внешний PDB, в файл не встроен) |
| Символы | COFF-таблицы нет; имя символа из файла не получить |

- Адрес загрузки: `0x10000000` (Preferred load address, см. map).
- Все переменные, с которыми работает FlexRouter (профиль profile001.ap),
  лежат в **`.data`** (RVA 0x9C000…0xFF364) — это обычные глобальные
  переменные C++ (`int`, `double`, `char`, массивы).
- Приборы (гейджи) — структуры `GAUGEHDR`/`ELEMENT_*` в `.data`, растры в
  `.rsrc`. Список гейджей — см. `analysis/gaugehdr_count.txt`.

### Именованные переменные FS9

Помимо глобальных переменных, гейдж использует **именованные переменные FS9**
(`register_named_variable` / `check_named_variable`) — строки вида
`PP_TKS_REZIM`, `AZS_DINAMIK`, `I21_N1_GOT`, `HYDRO_RA56_YAW1`, `PNK_azs_dme_1_2`.
Их полный список (192 шт., с RVA строк) — `analysis/named_variables.txt`.
FlexRouter к ним напрямую обратиться не может (значения хранятся в симуляторе),
но они полезны как документация «переменного пространства» борта.

## 2. Откуда взяты офсеты переменных

Проблема: офсеты для FlexRouter есть только в map-файле сборки автора.
В комплекте борта есть map-файлы
(`204_beta-2\Aircraft\PT_Tu-154M\Info\gau_maps\PNK_154M.map` и др.), но это
**другая сборка**: строки литералов лежат по другим адресам (сдвиг плавает
от −0xD0 до −0x160 по .data), напрямую офсеты не подходят.

Решение (реализовано в скрипте):

1. **Якоря** — `profile001.ap` содержит 246 переменных с офсетами
   `NN_pnk_154m_v1_40.GAU`. Все 246 адресов **подтверждены таблицей
   релокаций** поставляемого GAU (т.е. код реально обращается по этим
   адресам) → профиль соответствует именно этому GAU.
2. По именам символов (`NameInMapFile`) 245 якорей сопоставлены с map.
3. **Кусочно-линейная интерполяция** дельты (map_rva → shipped_rva) по
   якорям даёт офсеты остальных переменных. Точность (leave-one-out):
   медиана 32 байта, p90 = 88 байт.
4. **Проверка по релокациям**: predicted-адрес ∈ REFS (15902 цели-адреса из
   `.reloc`) → помечен «подтверждён». Это сильный признак: любой доступ к
   глобальной переменной из x86-кода проходит через абсолютный адрес,
   попадающий в таблицу релокаций.

### Итог по переменным NN_pnk_154m_v1_40.GAU

| Категория | Количество |
|---|---|
| Всего данных-символов в map (seg .data) | 5398 |
| Скаляры (`int/double/char/bool/…`) | 2308, из них **1597 подтверждено релокациями** |
| Массивы (первый элемент) | 9 |
| Указатели / структуры ELEMENT_* и пр. (внутренняя кухня гейджей) | ~3080 — в профиль не включены |
| Именованные переменные FS9 (строки) | 192 |

Размеры переменных восстановлены из MSVC-манглинга: `@@3HA` → `int`
(FourBytes), `@@3NA` → `double` (EightByteFloat), `@@3EA` → `unsigned char`
(Byte), `@@3_NA` → `bool` (Byte) и т.д.

## 4. Профиль `profile002.ap`

Сгенерирован по аналогии с `profile001.ap` (тот же формат: `Panels` +
`Variables ProcessToManage="fs9"`, тип `MemoryPatchVariable`):

- **12 панелей по подсистемам** (АЗС/Оверхед, ТКС/ПНП, АБСУ, РСБН, НВУ,
  ДИСС, электрика, СВС, радио, СПУ, двигатели, прочее) — распределение по
  префиксам имён (`azs_*`, `tks_*`, `absu_*` …).
- **2310 переменных** `MemoryPatchVariable`, у каждой заполнены
  `ModuleName`, `Offset`, `Size`, `NameInMapFile` (значит, работает
  штатный инструмент FlexRouter «обновить офсеты из map-файла»).
- В `Description` каждой переменной: C-тип, obj-подсистема, источник офсета
  и статус подтверждения.
- Секция `AccessDescriptors` не создаётся (загрузчик FlexRouter её
  допускает) — состояния кнопок/ламп настраиваются в UI роутера.

### Как пользоваться и предостережения

1. Скопировать `profile002.ap` в `FlexRouter\Configuration\Profiles\`.
2. Офсеты переменных бывают двух сортов:
   - **«profile001 (точный)»** — 246 шт., гарантированно верные;
   - **«map → интерполяция»** — расчётные; из них **1597 подтверждены
     релокациями** (высокая уверенность), остальные ~700 помечены в
     Description как «требует проверки» — их адрес кодом не используется
     напрямую (доступ через указатели/массивы) либо офсет неточен.
3. ⚠️ **Не** запускать «обновление офсетов из map-файла» с прилагаемым
   `PNK_154M.map` — он от другой сборки и сдвинет верные офсеты.
4. Первый включаемый сигнал для проверки: `elektro_out_bus27`
   (Offset `9C4A4`, Byte) — «общее питание от аккумулятора».

## 5. Как проверить/доизвлечь что-то ещё

```powershell
python analysis\extract_gau_variables.py
```

Скрипт сам разбирает PE, парсит map, строит якоря из `profile001.ap`,
интерполирует офсеты, проверяет их по релокациям и перегенерирует CSV и
`profile002.ap`. Для другого .gau (например `es_154m_3_112.gau`) —
заменить пути `GAU`/`MODULE` и взять соответствующий map из `gau_maps`.
